BEAT 2 — THE FILTERS ARE INSIDE THE INDEX
===============================================================================

SCREEN
    EXPLAIN, full frame. Hold it long enough to actually read. Highlight
    "vector search" and "prefix spans".

        • vector search
            table: party@party_shortlist
            target count: 20
            prefix spans: [/'1f9e6dd3…'/'amazon.titan-embed-text-v2'
                           /'counterparty'/'contactable' - …]

    Then two seconds of the static test failing against a deliberately broken
    query — proof the assertion is real and not decoration.

VO
    This is CockroachDB's vector index. Look at the plan: the filters live
    inside the index prefix. Tenant, model, contactable. The search runs in the
    filtered subspace — not a scan with a WHERE clause bolted on afterwards.

    And that prefix starts with tenant_id. The same column a static test proves
    every single statement in this codebase carries.

    One column. Our security boundary and our partition key at once.

    pgvector can do the similarity. It cannot make one decision do both jobs.

WHY
    "prefix spans" is the detail a technical judge reads as real. But the
    second half is the strongest idea in the system and has never been said out
    loud: filtered ANN and multi-tenant isolation fall out of ONE schema
    decision. Correctness and performance from the same column.

    The concession in the last line is doing work. It is the first of two
    places we hand the opposition its best argument, which is what makes the
    irreplaceable beats credible when they arrive.

DEPENDS ON  Nothing. Already true, already asserted by test_vector_plans.py on
            every run.
NOTE        Re-run EXPLAIN on the day. The model string reads Titan only if W5
            landed; openai:text-embedding-3-small is fine and changes nothing.

BEAT 3 — THE DATABASE IS THE RUNTIME
===============================================================================

SCREEN
    Three moves, fast:

    1. SHOW CHANGEFEED JOBS — one running job. A row written to outbox, and
       with no poller running anywhere, an agent run appears two seconds later.
    2. kill -9 across half the fleet. The work still completes.
    3. lease_race_demo.py Act 2 — both workers named ingest-cli:

           terminal 1 claims b844314c…  owner=ingest-cli  token=2bb498ed…
           terminal 2 claims b844314c…  owner=ingest-cli  token=6f72beda…
           terminal 1 tries to complete -> REFUSED: lease lost
           terminal 2 completes         -> OK

VO
    No orchestrator. Agents never call each other — a changefeed on the memory
    tables wakes the next one. The database is the event bus.

    So kill half the fleet mid-run. The work still finishes. A dead worker's
    lease expires and the row comes back on its own.

    And the one thing we can never take back — the send — commits its claim
    before the network call. Two workers, same name, one lead. The name cannot
    tell them apart. The token can.

    Serializable by default. A fence that fails closed.

WHY
    The brief's headline criterion is "memory as integral to agent
    functionality — not supplementary". This is the sharpest available answer:
    the memory layer is not where agents look things up, it is what makes them
    run at all. A row changing IS the scheduling primitive.

    Merging the lease token in here is what makes the beat land. Alone it was a
    correctness footnote; here it completes the thought — the database starts
    the work AND refuses the work that should not happen. Same substrate, both
    directions.

    A missed pitch costs nothing. A second pitch to a curator who already got
    one costs us that curator permanently. That asymmetry is why the fence
    fails closed.

DEPENDS ON  W2 (changefeed to Lambda). The lease half is already built.
FALLBACK    If W2 slipped, cut the first paragraph and open on kill -9. Do NOT
            soften it to "the database could wake agents" — SHOW CHANGEFEED
            JOBS returning nothing is a ten-second falsification. The beat
            still works as a resilience-and-refusal beat.

BEAT 4 — THE ROW LIVES WHERE THE LAW SAYS
===============================================================================

    *** ARGUMENT BEAT. Slow down. Let the two rows sit on screen. ***

SCREEN
    SHOW RANGES FROM TABLE contact_route. Two rows, side by side, held:
    one US contact on us-east-1 replicas, one EU contact on eu-west-1.
    Same table. Same query. Different continents.

        SHOW SURVIVAL GOAL FROM DATABASE defaultdb;   ->  region

    Then take a region offline. The shortlist keeps answering.

VO
    We email real people. So we hold real data about them — and European law
    says where that data may live.

    Same table. Same query. This row is in Virginia. This one is physically in
    Ireland, because she is a European contact.

    One logical table. Residency per row, enforced by the database instead of
    by us remembering. In Postgres that is three databases and a
    synchronisation problem you own forever.

    Now lose a region. It keeps answering.

WHY
    This answers "why not Postgres" with no hedging at all.

    It matters that it is contact_route specifically. That table holds personal
    data for named individuals our agents actually contact. This is not a
    synthetic demo of a feature — it is the one table where residency is a
    legal obligation rather than an architectural preference.

    "Because she is a European contact" is deliberate. A person, not a row.
    The whole video is about a system that acts on people.

DEPENDS ON  W1 (three-region cluster, REGIONAL BY ROW, SURVIVE REGION FAILURE).
FALLBACK    CUT THE BEAT ENTIRELY and say nothing about regions. SHOW REGIONS
            on Basic returns one row and a judge checks it instantly. Beat 5
            can carry the irreplaceability argument alone — it is strong enough.
IMPORTANT   The hosted demo runs single-region on Basic. This beat is filmed
            against an ephemeral cluster stood up from committed Terraform and
            torn down after. THE SUBMISSION TEXT MUST SAY SO PLAINLY. See WHAT
            MUST NOT BE SAID, item 1.

BEAT 5 — WHAT DID IT BELIEVE, WHEN IT ACTED?
===============================================================================

    *** THE CENTREPIECE. Give it the most room. Nothing else in this video is
        Postgres-impossible at any price. This is. ***

SCREEN
    A sent message in the console. Click through to the ranking that justified
    it. Then the same shortlist query, twice, side by side:

        - now
        - AS OF SYSTEM TIME, at the exact timestamp stamped on that send

    Different rankings. Same query. Highlight the four words of SQL, and the
    lesson row that moved her.

VO
    We emailed this curator on Tuesday. Why her?

    Here is the same shortlist, re-run against the memory exactly as it was at
    the moment we sent. Same index. Same embeddings. Same lesson that moved her
    up four places.

    Four extra words of SQL. No audit table. No event log. No versioned copy of
    anything.

    Every agentic system can tell you what it knows. This one tells you what it
    believed, when it acted.

    Postgres cannot do that at any price.

WHY
    Every agentic memory demo answers "what does the agent know". Almost none
    answers "why did it decide that, THEN" — because answering it normally
    means building an event-sourcing subsystem: temporal tables, a versioned
    copy of every embedding, an audit log of every rerank. And even then you
    only replay what you thought in advance to record.

    AS OF SYSTEM TIME replays state nobody chose to record — including the
    vector ranking itself. That is the difference between an audit log and a
    time machine.

    "What it believed, when it acted" is the line the whole video is built to
    earn. Do not step on it. Let it sit before the close.

    The moral weight is the point: this system emails strangers. Reconstructing
    the exact belief state behind an irreversible act is not a feature. It is
    the condition for being allowed to run it at all.

DEPENDS ON  W3 (time travel on the production path + outreach audit trail).
CONSTRAINT  Reachable depth is governed by gc.ttlseconds and is roughly TEN
            HOURS today, not seven days — the GC threshold only moves forward
            from when it was raised. Pick a send inside the window. If asked:
            "seven days of retention from the day we raised it; ten hours
            available today."

WHAT MUST NOT BE SAID
===============================================================================

1. DO NOT IMPLY THE HOSTED DEMO IS MULTI-REGION. It runs on Basic,
   single-region. Beat 4 is filmed against an ephemeral cluster. The submission
   must say, in plain words: "the hosted demo runs single-region; the
   multi-region topology is reproducible from the committed Terraform in under
   twenty minutes and is shown in the video." A claim a judge can falsify with
   one SHOW REGIONS is worse than no claim — and that rule does not relax
   because the capability is real but not currently deployed.

2. NO SCALE CLAIMS. 175k is twelve times where we started and enough to make
   the index necessary. It is not a distributed-systems problem, and saying it
   is invites the one comparison we lose. Label the benchmark with its N.

3. DO NOT CLAIM SEVEN DAYS OF TIME TRAVEL. Ten hours is what the cluster can
   serve today.

4. DO NOT CLAIM ANY BEAT WHOSE WORKSTREAM SLIPPED. Every beat has a fallback
   for exactly this reason. Cutting a beat costs fifteen seconds. Getting
   caught costs the submission.

5. NO FEATURE TOUR. Every capability named here is named because it does a job
   in this product. If it has no job, it is not in the video, however
   impressive it sounds.
