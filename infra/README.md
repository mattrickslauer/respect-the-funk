## The label-scope architecture

> **AWS runs the logic; B2 holds the bytes and the provenance.**

Five things to think about. One of them is durable.

| # | Service | Role | Why it costs nothing at rest |
|---|---|---|---|
| ① | **Lambda** (`web`) | FastAPI via Lambda Web Adapter + Function URL. JSON only. | No provisioned concurrency |
| ② | **SQS** | One job queue + DLQ. Generation is minutes; it can never be a request. | Pay-per-request, 1M/mo free |
| ③ | **AWS Batch on Fargate Spot** | One container: Genblaze fan-out **and** ffmpeg. | `minvCpus: 0` |
| ④ | **SSM Parameter Store** | B2 + provider credentials. | Standard tier is free |
| ⑤ | **Backblaze B2** | Artists, identities, songs, masters, kits, manifests. Everything durable. | $6/TB-mo |

Plus ECR (image storage, ~cents) and CloudWatch (logs at 14-day retention, ~cents), which come along for the ride rather than being designed in.

**Realistic idle cost: under $1/month** — B2 storage and a container image. No compute floor anywhere.

### The move that made it simple: there is no database

This is the whole simplification, and it is worth stating plainly because it looks like an omission.

The relational schema in BUILD-SPEC §3 exists almost entirely to serve **fans**. Attribution joins, leaderboard views, click ledgers, reward rows, invite/K-factor tracking — those are the things that need SQL. PRODUCT.md defers all of them, and the pressure for a database tier goes with them.

What the label actually needs to store is **documents**: an artist, an identity, a song's measurements, an edit, a generated kit. The repo is already excellent at exactly this — plain-text YAML sidecars, content-addressed media, a resolver that walks up to find the root. That model doesn't need Postgres; it needs a bucket, and B2 is the bucket.

For listing and search, Genblaze already emits the index: `genblaze index` → `manifests.parquet` in B2, queryable directly by Athena, no server. That is BUILD-SPEC's own "analytics-ready" artifact doing double duty as the catalog.

**When to revisit:** the moment role 2 comes back. Attribution and leaderboards are relational and should not be faked on top of Parquet.

> **It came back earlier than expected, on a branch.** [MEMORY-SPEC.md](../MEMORY-SPEC.md) reintroduces a database tier — CockroachDB — for a requirement this analysis did not consider: **filtered vector retrieval** over the clip corpus, where `rights.source` is a predicate inside the similarity query rather than a filter applied afterwards. Parquet + Athena is an analytics path and cannot serve that at interactive latency. That branch is taken after the Aug 3 submission; the architecture on this page ships unchanged.
>
> **The cost conflict has since been priced, and it is not a conflict.** [MEMORY-WORKLOAD.md](./MEMORY-WORKLOAD.md) closes MEMORY-SPEC §10 decision 2: CockroachDB Basic starts at $0/month, scales to zero, and gives 50M Request Units + 10 GiB of storage free every month, with the vector index included on that plan. The workload fits inside the free allowance at every tier modelled — so **the "under $1/month idle" claim above survives the branch**, and the database contributes **$0.00** of it. The binding constraint turns out not to be price at all: it is that the RU cost of a filtered vector scan is unpublished and must be measured.
>
> **The picture is [`memory-branch.pdf`](./memory-branch.pdf)** — the same five services plus the tier, drawn to make two things unmissable: CockroachDB holds *vectors and rows, never bytes* (B2's role is untouched, and the presigned browser↔B2 path is still the only way an asset moves), and the teal edges form a **cycle** rather than a fan-in. A memory tier with only read edges is a catalog, which is precisely what this section says a bucket already does.

### What deferring the fan side removed

Against `deferred-marketplace.pdf`: **CloudFront**, the **CloudFront Function + KeyValueStore** `/r/{code}` redirect, **Aurora Serverless v2** (and its 0-ACU resume problem), **EventBridge Scheduler** and the separate indexer Lambda, and the split between `kit-worker` and `composite-worker` — there is one generator now, because there are no fan composites to build.

Eleven services became five. No CDN is needed until an audience exists; until then the label is a handful of authenticated users pulling assets over presigned URLs.

## Why this is AWS and not BUILD-SPEC's GCP

BUILD-SPEC §2 locked Cloud Run + Cloud Tasks + Neon. That was sound; the target moved. The useful finding is that **§2b's eight scalability rules survive the move unchanged**, because they are about shape — queue the long work, keep bytes off the app server, make jobs idempotent — not about vendor.

| BUILD-SPEC §2 (GCP) | Here (AWS) |
|---|---|
| Cloud Run, `min-instances=0` | Lambda + Web Adapter + Function URL |
| Cloud Tasks | SQS + DLQ |
| Cloud Run Job | AWS Batch on Fargate Spot |
| Neon Postgres | *nothing* — see above |
| Secret Manager | SSM Parameter Store (free tier; Secrets Manager is $0.40/secret/mo, a real floor against "$0 idle") |
| **Backblaze B2** | **unchanged** — 1 of 4 scoring criteria |
| **Genblaze** | **unchanged** — likewise |

## Caveats that still apply

**1. The generator is Batch, not Lambda — deliberately.**
BUILD-SPEC §4 calls Genblaze with `timeout=900`. That is *exactly* Lambda's 15-minute ceiling, with no headroom for cold start, provider retries, or the upload afterwards, and it would fail by silent timeout on the most expensive path in the system. Batch has no such limit and still sits at zero via `minvCpus: 0`. This is the one place the obvious GCP→AWS mapping is actively wrong.

**2. Fargate Spot is safe only because jobs are idempotent.**
§2b rule 4 is load-bearing: jobs keyed by input hash mean a Spot reclaim mid-render costs wall-clock and nothing else. Relax that rule and Spot must become on-demand.

**3. B2 egress is billed when it leaves Backblaze.**
The free-egress arrangement is with **Cloudflare**, not AWS. At label scale — a few users pulling assets — this is pennies. It only becomes a line item if role 2 returns and fans start pulling at volume, at which point Cloudflare in front of B2 makes it $0. Worth knowing now rather than on a bill.

**4. Approval state has no home yet.**
PRODUCT.md flags that nothing carries `draft | approved | published`. That is a data-model gap, not an infrastructure one, but it is the first thing that will want a real row somewhere. If it turns out to need queryable state, DynamoDB on-demand ($0 idle) is the answer that does not reintroduce a database tier.

*Superseded on the memory branch:* [MEMORY-SPEC §4](../MEMORY-SPEC.md) gives approval its row in CockroachDB alongside the episode and identity tables, because that branch is paying for the tier anyway. On this architecture the DynamoDB answer still stands.

## Deliberately not here

EKS/Kubernetes, multi-region, a VPC with NAT gateways (a NAT is ~$32/month of pure idle floor and would defeat the premise on its own), API Gateway (Function URLs are free and sufficient), Step Functions (one queue and one job need no orchestrator), Cognito (a single tenant with a handful of users does not need a user-pool service), and any warm pool anywhere.

## Next step

A shape to approve, not code to run. Once agreed, `infra/terraform/` gets: ECR + one image build, the Lambda/Function-URL pair, SQS + DLQ, a Batch compute environment at `minvCpus: 0`, and the SSM parameters. That is a genuinely small amount of HCL — which is the point.
